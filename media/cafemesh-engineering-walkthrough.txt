This is the CaféMesh AI engineering walkthrough: how the application connects real customer needs to café operations, how its agents use evidence, what the backend protects, and how we test the result. The public demo is hosted on Google Cloud Run and reached through cafemesh dot stackclimb dot com.

The browser app is React, Vite, and TypeScript. FastAPI owns the business rules, provider adapters, stored events, authentication checks, and action boundaries. Locally the app can use SQLite; this public demo uses a Firestore-backed synthetic-state adapter. One service serves the built UI and API. Google Sign-In is required for reviewer views, while public customer actions remain synthetic.

Four Google ADK agents have narrow roles. Concierge coordinates intent and workflow. TasteSafety reads the menu and safety records. VisitOrder reads queue and seating context and prepares proposals. OpsOwner reads recorded metrics and suggests grounded operational next steps. Their tools return structured facts; the model does not get a write tool for orders, inventory, or staff changes. The deployed customer path has recorded live Gemini and ADK tool outcomes.

Retrieval is matched to the data. CaféMesh currently filters a small structured menu using exact names and explicit lexical synonyms, then checks the authoritative records in code. That is neither embeddings nor RAG. For prices, ingredients, allergens, stock, and queue values, typed fields are a more reliable source than a vector index. A governed document RAG layer makes sense later for long café procedures and policies, with tenant filters, timestamps, source citations, no-answer thresholds, and its own retrieval evaluation set.

An inspection of the live application exposed a useful failure mode: generated prose could describe an allergy and visit-time constraint that the guest had not entered. The fix is at the response boundary. When an allergy is explicit, CaféMesh withholds free-form model narration and shows the backend’s structured candidates, evidence IDs, conflict reasons, and staff-review state. The model cannot override that result. The deterministic regression suite also checks that an allergy assurance is never shown.

The request workflow is staged. The API retrieves structured menu and visit facts through narrow ADK tools, asks the coordinator to prepare a response, and records tool status, evidence, and latency. Backend eligibility logic applies the extracted budget, temperature, diet, allergy, availability, cross-contact, and visit-time constraints. An exact item lookup can narrow the list; an unsupported smoothie request returns no match. If Vertex AI times out, the UI surfaces the failure and does not label a demo answer as live success.

Actions have separate gates. A recommendation is not an order. The customer previews a specific item and price, then confirms explicitly. The backend binds that confirmation to the exact proposal, rechecks price, availability, opening state, safety, and timing, and uses idempotency to prevent duplicates. The synthetic Operations order appears only after confirmation. Staff state transitions are validated; measured preparation time is distinct from an estimate. Manager accept and reject decisions are audited, while acceptance is not execution.

Location is also explicit. Google Places returns public directory listings and Routes calculates walking time. The default is Indiranagar Metro Station, Bengaluru. Visitors can type another landmark or choose the browser’s one-time location control. The browser asks permission only after that choice; coordinates are sent for the live request and are not persisted. Maps listings remain separate from participating-café menus or order systems.

The Operations dashboard is derived from shared records and events. It exposes order flow, stock and occupancy alerts, safety review, provider health, tool successes and errors, latency, preparation calibration, manager decisions, and unpromoted AI-quality signals. Owner metrics use the same records with an explicit time window and formulas. Empty data remains insufficient data. These are demo operations metrics, not production SLOs.

Verification now includes deterministic policy tests and a small versioned menu-retrieval golden set: the canonical severe-peanut request, a hot espresso lookup, and an unsupported smoothie. The cases check eligible results, staff-review results, and blocked items. Tests also cover confirmation, failures, idempotency, location handling, feedback boundaries, and owner calculations. The current golden set is small; it is not evidence of broad semantic-retrieval performance.

There is no LLM-as-a-judge pipeline in this release. That is deliberate honesty. A responsible next step is to collect reviewed prompts and answer rubrics, run deterministic gates first, then compare any qualitative model judge against human labels and report agreement. Rejected answers and provider errors can be reviewed, but they never rewrite prompts, permissions, or guardrails automatically.

The customer taste, Operations preparation, and AI-quality loops have separate boundaries. Explicit taste choices can change bounded preference weights. Preparation estimates calibrate only from measured outcomes after enough samples. AI-quality cases need human approval and regression checks before promotion. Allergies never enter preference learning.

For a production café pilot, the roadmap is split into end-to-end customer and operations slices, supported by shared identity, trusted data, transactional storage, privacy, reliability, and AI-quality foundations. It adds tenant isolation, staff roles, owner administration, source record versioning, transactional stock, customer consent and deletion, cancellation and notification flows, backup and restore, budget alerts, and production service objectives. Later slices include reservations, group planning, POS and payment integrations, forecasting, Gemini Live voice, BigQuery, Model Armor, and multi-location analytics. The future agent harness should trace each workflow and tool, measure grounding, policy compliance, latency, cost, and outcomes, and replay failures against reviewed golden and adversarial evaluations. Document RAG is useful for governed café procedures, with citations and retrieval evaluation; structured menu and allergen facts should continue to come from authoritative tools. An LLM judge can help score qualitative quality only after calibration against human labels. It never decides safety. Safe self-healing means detecting failures, using bounded retries for idempotent operations, opening a review candidate, or routing to a human. Agents must not rewrite deployed prompts, permissions, or guardrails and promote the change themselves. Human review, regression checks, staged rollout, monitoring, and rollback remain release gates. These are roadmap capabilities until they are implemented and verified.

This is forward-deployed engineering in practice: understand the business workflow, turn it into explicit contracts, connect systems through narrow adapters, protect high-impact actions, evaluate the exact behaviors, observe real outcomes, and keep the roadmap grounded in the operating model.
